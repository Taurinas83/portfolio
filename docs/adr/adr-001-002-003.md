# ADR-001: Hexagonal Architecture sobre MVC Tradicional

## Status
**ACCEPTED**

## Contexto
O Assessor Pessoal PWA requer alta testabilidade, manutenção de longo prazo e capacidade de trocar componentes (ex: provider de IA, backend) sem refatoração massiva. Usuários TDAH precisam de resiliência (offline-first) e performance consistente.

## Decisão
Adotar **Hexagonal Architecture (Ports & Adapters)** em vez de MVC tradicional para a estrutura do projeto.

### Estrutura Proposta
```
src/
├── domain/           # Core business logic (independente de frameworks)
│   ├── scheduling/   # Regras de agenda, buffer, reprogramação
│   ├── integration/  # Contratos de sync Google
│   ├── intelligence/ # Priorização IA, contextos TDAH
│   ├── notification/ # Alertas escalonados
│   └── compliance/   # LGPD/GDPR, consentimentos
├── application/      # Casos de uso (orquestram domain)
├── infrastructure/   # Implementações concretas (Google API, Supabase, etc.)
└── interfaces/       # Controllers, Presenters, Views (PWA React)
```

### Justificativa Técnica
| Critério | Hexagonal | MVC |
|----------|-----------|-----|
| Testabilidade unitária | Alta (mocks via ports) | Média (acoplamento framework) |
| Troca de provider IA | Alterar adapter apenas | Refatorar controllers |
| Offline-first natural | Sim (domain não sabe de rede) | Complexo (lógica misturada) |
| Compliance injetável | Sim (port de audit) | Acoplado ao modelo |
| Curva de aprendizado | Moderada | Baixa |

## Consequências

### Positivas
- ✅ **Testes unitários puros**: Domain logic testável sem DB/API
- ✅ **Vendor lock-in reduzido**: Trocar OpenRouter → Together AI é apenas novo adapter
- ✅ **Compliance by design**: Port de `AuditTrail` injetado em todos os casos de uso
- ✅ **Offline-first natural**: Domain não sabe se dados vêm de IndexedDB ou API
- ✅ **Feature flags isoladas**: Adapters condicionais por tier

### Negativas
- ❌ **Boilerplate inicial**: Mais arquivos que MVC
- ❌ **Curva de aprendizado**: Equipe precisa entender Ports/Adapters
- ❌ **Over-engineering risco**: Para MVP simples, pode parecer excesso

## Mitigações
1. **Templates de código**: Gerar estrutura base via CLI
2. **Documentação viva**: Exemplos de ports/adapters no `/docs`
3. **Code review focado**: Garantir que domain permaneça puro

## Conformidade com PRD
- **ASR-01**: ✅ Atendido (Hexagonal sobre MVC)
- **FR-02**: ✅ IA triage isolado em `domain/intelligence`
- **FR-04**: ✅ Compliance port injetável
- **NFR-01**: ✅ Domain não introduz latência

## Referências
- [Ports and Adapters - Alistair Cockburn](https://alistair.cockburn.us/hexagonal-architecture/)
- [Clean Architecture - Robert Martin](https://blog.cleancoder.com/clean-architecture-series/)
- [DDD Bounded Contexts](https://martinfowler.com/bliki/BoundedContext.html)

# ADR-002: Edge Functions para Sync (Serverless)

## Status
**ACCEPTED**

## Contexto
Sync bidirecional Google Calendar/Tasks requer webhooks, processamento delta e resolução de conflitos. MVP precisa operar em free tier (CAC ≈ R$0) com escala automática para validação.

## Decisão
Usar **Edge Functions (Supabase/Cloudflare Workers)** para processamento de sync em vez de monolito ou serverful (EC2, VM).

### Arquitetura Proposta
```
Google Pub/Sub Webhook
    ↓ HTTPS
Edge Function (sync-handler)
    ↓
[Processamento Delta]
    ↓
[Resolução Conflitos]
    ↓
Supabase PostgreSQL
```

### Comparação de Abordagens

| Critério | Edge Functions | Monolito (EC2) | Serverful (Lambda) |
|----------|----------------|----------------|-------------------|
| Custo inicial | R$0 (free tier) | ~R$50/mês | ~R$0.20/invocação |
| Escala | Automática | Manual (auto-scaling) | Automática |
| Cold start | < 50ms | N/A | 100-500ms |
| Complexidade deploy | Baixa (git push) | Alta (CI/CD infra) | Média |
| Vendor lock-in | Moderado (Supabase) | Baixo | Alto (AWS) |
| SLA nativo | 99.5% | Depende config | 99.9% |

### Justificativa de Negócio
- **CAC baixo**: Infra gratuita até ~10k usuários/mês
- **Margem >80%**: Sem custo fixo de servidor
- **Validação rápida**: Deploy em minutos, rollback instantâneo
- **Escala elástica**: Picos de sync (segunda-feira manhã) sem intervenção

## Consequências

### Positivas
- ✅ **Custo operacional mínimo**: Free tier cobre MVP completo
- ✅ **Deploy automático**: Git push → production em < 2min
- ✅ **Latência baixa**: Edge próximo ao usuário (P95 < 300ms)
- ✅ **Rate limiting nativo**: Cloudflare WAF incluso
- ✅ **Observabilidade**: Logs integrados com Supabase dashboard

### Negativas
- ❌ **Vendor lock-in moderado**: Migrar Supabase → outro requer refactor de adapters
- ❌ **Limites de execução**: 10s timeout max (mitigado com async processing)
- ❌ **Debug distribuído**: Tracing requer OpenTelemetry setup

## Mitigações
1. **Hexagonal adapters**: Isolar lógica de Edge Function para facilitar migração
2. **Async processing**: Jobs longos → fila + worker separado
3. **OpenTelemetry**: Instrumentação desde o dia 1

## Conformidade com PRD
- **stack_proposal_free_tier**: ✅ Supabase Edge Functions
- **NFR-01**: ✅ P95 < 300ms (edge latency)
- **monetization**: ✅ Metering injetável no adapter
- **security.zero_trust**: ✅ Edge WAF + rate limit nativo

## Referências
- [Supabase Edge Functions](https://supabase.com/docs/guides/functions)
- [Cloudflare Workers Pricing](https://workers.dev/pricing)
- [Serverless Best Practices](https://aws.amazon.com/serverless/serverless-best-practices/)

# ADR-003: LLM Externo via Proxy (Não Embutido)

## Status
**ACCEPTED**

## Contexto
Priorização de tarefas com contexto TDAH requer inferência de IA (LLM). MVP precisa controlar custos de inferência, permitir troca de provider e manter fallback heurístico.

## Decisão
Usar **proxy dedicado** para LLM externo (OpenRouter/Together AI/Qwen) em vez de modelo embutido (fine-tune local) ou API direta do frontend.

### Arquitetura Proposta
```
Frontend PWA
    ↓ HTTPS
Edge Function (ai-proxy)
    ↓ [Model Routing]
    ├→ OpenRouter (gpt-4o-mini)
    ├→ Together AI (llama-3-70b)
    └→ Qwen Free Tier (fallback)
    ↓
[Response + Metering]
    ↓
Frontend PWA
```

### Comparação de Abordagens

| Critério | Proxy Externo | Modelo Embutido | API Direta (frontend) |
|----------|---------------|-----------------|----------------------|
| Custo inicial | Pay-per-use (~R$0.002/inferência) | Treino: ~R$500+ | Pay-per-use |
| Controle de custos | Alto (metering + routing) | Baixo (infra fixa) | Nenhum (chave exposta) |
| Troca de modelo | Imediata (config) | Requer retreino | Imediata |
| Segurança | Chaves no backend | Chaves no backend | ❌ Chave no frontend |
| Latência | +50-100ms (proxy) | Baixa (local) | Baixa (direta) |
| Fallback heurístico | Fácil (proxy decide) | Complexo | Difícil |

### Justificativa de Negócio
- **Metering preciso**: Cada inferência logada com custo em micro-centavos
- **Model routing**: Escolher modelo por custo/qualidade dinamicamente
- **Upsell habilitado**: Tier free usa Qwen free, Pro usa GPT-4o
- **Segurança**: Chaves de API nunca expostas no frontend

## Consequências

### Positivas
- ✅ **Controle de margem**: Custo por inferência conhecido, repassável no billing
- ✅ **Flexibilidade**: Trocar OpenRouter → Together AI sem deploy do frontend
- ✅ **Fallback transparente**: Se LLM falha, proxy retorna heurística
- ✅ **Feature flags**: `ai_scheduling` flag controla acesso no proxy
- ✅ **Compliance**: Audit trail de prompts/responses no backend

### Negativas
- ❌ **Latência adicional**: +50-100ms do proxy (mitigado com edge)
- ❌ **Dependência externa**: Provider indisponível afeta feature
- ❌ **Custo variável**: Picos de uso impactam margem (mitigado com rate limit)

## Mitigações
1. **Edge proxy**: Rodar proxy em Edge Function para minimizar latência
2. **Circuit breaker**: Se provider falha 3x, switch automático para fallback
3. **Cache de respostas**: Prompts idênticos retornam cache (5min TTL)
4. **Rate limit por usuário**: Evitar abuso em tier free

## Prompt Template (Exemplo)
```json
{
  "system": "Você é um assistente de priorização de tarefas para usuários com TDAH.",
  "user": {
    "tasks": [...],
    "context": {
      "adhd_profile_active": true,
      "buffer_minutes": 15,
      "focus_block_minutes": 45,
      "current_time": "2024-01-15T14:30:00Z",
      "energy_level": "medium"
    }
  },
  "response_format": {
    "task_id": "uuid",
    "priority_score": 1-10,
    "reason_code": "time_pressure|context_match|...",
    "suggested_start": "ISO8601"
  }
}
```

- **ASR-03**: ✅ LLM externo via proxy
- **FR-02**: ✅ IA triage com reason_code
- **monetization.metering**: ✅ ai_triage_runs logado
